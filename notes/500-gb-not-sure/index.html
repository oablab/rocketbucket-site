500 GB went up. The app said it wasn't sure.

September 8, 2026 · Resumable uploads to S3 and R2

We put a 500 GB file through RocketBucket to Cloudflare R2 — 9,847 parts. The design for resuming an interrupted upload had been through five rounds of review and was, as far as anyone could tell, correct. The run failed three times anyway, and not one of the failures was in the design.

What "resume" has to promise

S3 and everything that speaks its API upload big files in parts: at most 10,000 of them, each between 5 MiB and 5 GiB. For 500 GB that arithmetic forces a part of at least 52 MB, so RocketBucket ignores its usual 8 MiB default and picks 52 MiB for this file before the upload starts. Five parts are in flight at once — about 260 MB of memory, which is the whole budget a transfer is supposed to need.

If the connection drops at part 6,000, "resume" means keeping the same upload ID and not sending those 6,000 parts again. The danger is obvious once you say it out loud: what if the file changed in between? You would glue the first half of the old file to the second half of the new one and the server would happily call it an object. So every part is recorded the first time it is fully read — number, byte count, SHA-256 — and a part is skipped only when it is both on the server and matches that record. Across sessions the records live in a small journal on disk, written only after a part actually succeeded and deleted only after the completion is proven. We keep our own SHA-256 rather than trusting the server's ETag, because under SSE-KMS the ETag is not the part's MD5 and there is nothing to compare against.

One more rule, learned from watching other tools: incomplete multipart uploads are invisible in a normal listing and they are billed until someone aborts them. RocketBucket shows them, but never aborts one it did not create. Another client may own it.

14.5 GB of memory to skip 9,800 parts

We interrupted the 500 GB upload and resumed it. Memory climbed to 14.5 GB and macOS killed the process. A fresh upload of the same file sits at 700–900 MB.

The first suspect was the journal. It rewrote the whole file on every part — at 10,000 parts that is 10,000 rewrites of a JSON document that grows each time, quadratic work on the disk. We batched it to every 64 parts, made a failed write stay pending instead of silently vanishing, and reran. Memory climbed to 14.5 GB and macOS killed the process. The fix was correct and it was not the fix.

The real cause was in how "skip" was implemented. To verify a part before skipping it, the resume pass read the file from byte zero and hashed every part — including the 9,800 already on the server — in one tight loop that never paused. Each part left behind a little cloud of temporaries, and one of them was embarrassing: the hex encoding used String(format:), which allocates an Objective-C string per byte. Roughly 127,000 small allocations that nothing ever drained.

The structural fix: when the journal exists and the source is a local file, read only the parts that are missing, by byte range, and never touch the ones already uploaded. Their content is vouched for by the file's identity — size, modification date, and the inode, so a same-size replacement is caught — plus the journal's hash. A resume where every part is already there now reads zero bytes from disk and issues zero uploads; there is a test that asserts exactly that at 10,000 parts. The real 500 GB resume that used to die now stays under 500 MB when nothing is missing, and around 700 MB to 1 GB while it fills the gaps.

Review found what the fast path skipped

The ranged fast path went to review and came back with two must-fixes. It did not check that a range read returned every byte it asked for — a short read of the final part would have completed a truncated object, and the server would have accepted it. And it called CompleteMultipartUpload directly, skipping the reconciliation logic the slow path had. Both are fixed; a short read now fails the upload and keeps the journal for the next attempt.

It finished, and said it wasn't sure

Then the whole thing went through. All 500 GB. And the log said: upload completion is uncertain, please verify the object manually.

We checked R2. The object was there: 536,870,912,000 bytes, 9,847 parts, our commit marker in its metadata, no leftover multipart upload. A complete success reported as a failure.

When RocketBucket sends the final Complete request it stamps the object with a random token, so that if the response is lost it can ask the server afterwards "is the object there, with my token, at my size?" and know the answer is about its own upload and not someone else's same-size file. That question has a timing problem at this scale. R2 acknowledges the Complete and then spends tens of seconds assembling 9,847 pieces into one object. During that window the object does not exist yet and the multipart upload is already gone. Our check saw "upload gone, object absent," tried three times with at most four seconds between them, and concluded it could not know.

It now waits the way a large completion deserves — six attempts, 2, 4, 8, 15, 15, 15 seconds — and treats "the upload is gone" as ambiguous rather than as failure. What counts as success did not change: the object must answer, carry our token, and be exactly the expected size. If the token or size is wrong we still say we are not sure. We would rather admit uncertainty than claim an object that is not ours.

The design document had a section for every one of these situations, and every section was right. The failures were in the three things a design document does not contain: an allocator, a file that grows, and a server that needs half a minute to glue nine thousand pieces together. You do not find those by reviewing. You find them by uploading 500 GB.

Where this stands. Same-session and cross-session resume are in the current build, for local files uploading to S3-compatible storage. A cloud-to-cloud resume (S3 → R2, say) still re-reads the source, because it has no byte-range reader yet; a ranged GET is the next piece of work.

500 GB 傳完了，App 卻說它不確定

2026 年 9 月 8 日 · S3 與 R2 的斷點續傳

我們用 RocketBucket 把一個 500 GB 的檔案送上 Cloudflare R2——9,847 個分段。斷點續傳的設計經過五輪 review，就所有人看得出來的部分而言，它是對的。這一趟還是失敗了三次，而三次都不在設計裡。

「續傳」要承諾什麼

S3 和所有說 S3 協議的服務，大檔案都是分段上傳：最多 10,000 段，每段介於 5 MiB 到 5 GiB。500 GB 算下來，每段至少要 52 MB，所以 RocketBucket 會放棄平常 8 MiB 的預設，在上傳開始前就替這個檔案選定 52 MiB。同時有五段在傳——大約 260 MB 的記憶體，這應該就是一次傳輸需要的全部預算。

如果連線在第 6,000 段斷掉，「續傳」的意思是：沿用同一個 upload ID，那 6,000 段不要重送。危險之處說出來就很明顯：萬一中間檔案被改過呢？你會把舊檔的前半黏上新檔的後半，而 server 會很樂意把它當成一個物件。所以每一段在第一次完整讀到時就會被記錄下來——編號、位元組數、SHA-256——一段只有在「server 上有」而且「跟記錄相符」兩個條件都成立時才會被跳過。跨 session 的話，這些記錄住在磁碟上一個小小的 journal 裡，一段真正傳成功之後才寫入，完成被證明之後才刪除。我們自己算 SHA-256，不信任 server 的 ETag，因為在 SSE-KMS 之下 ETag 不是該段的 MD5，根本沒東西可以比。

還有一條規則，是看別的工具學到的：未完成的分段上傳在一般列表裡看不見，而且在有人 abort 之前會一直計費。RocketBucket 會把它們顯示出來，但絕不 abort 一個不是自己建立的。那可能是別的 client 的。

跳過 9,800 段，用了 14.5 GB 記憶體

我們把 500 GB 的上傳中斷，再續傳。記憶體爬到 14.5 GB，macOS 把 process 殺了。同一個檔案從頭傳，只用 700 到 900 MB。

第一個嫌犯是 journal。它每傳一段就把整個檔案重寫一遍——10,000 段就是重寫 10,000 次一份越寫越大的 JSON，磁碟上的平方級工作量。我們改成每 64 段批次寫一次，讓寫入失敗時保持待處理而不是默默消失，然後重跑。記憶體爬到 14.5 GB，macOS 把 process 殺了。這個修正是對的，而它不是那個修正。

真正的原因在「跳過」是怎麼實作的。為了在跳過之前驗證每一段，續傳那一趟從第 0 個位元組開始讀檔、把每一段都 hash 一遍——包括 server 上早就有的那 9,800 段——在一個從不暫停的緊迫迴圈裡。每一段都留下一小團暫存物件，其中一個很難為情：轉十六進位用的是 String(format:)，每個位元組配置一個 Objective-C 字串。大約 127,000 個小配置，沒有任何東西去回收它們。

結構性的修法：當 journal 存在、而且來源是本機檔案時，只依位元組範圍讀那些缺少的段，已經傳上去的一段都不碰。它們的內容由檔案的身分擔保——大小、修改時間、加上 inode，所以同樣大小的替換檔會被抓到——再加上 journal 裡的 hash。一次每段都已經在 server 上的續傳，現在從磁碟讀零個位元組、送出零次上傳；有一個測試在 10,000 段的規模上恰恰斷言這件事。原本會死掉的那個真實 500 GB 續傳，現在在沒有缺段時停在 500 MB 以下，補缺段時大約 700 MB 到 1 GB。

Review 找到了快速路徑跳過的東西

依範圍讀取的快速路徑送去 review，帶回兩個必修項。它沒有檢查一次範圍讀取是否真的回傳了要求的每一個位元組——最後一段若讀短了，會完成一個被截斷的物件，而 server 會接受。它還直接呼叫 CompleteMultipartUpload，繞過了慢速路徑有的核對邏輯。兩個都修了；讀短現在會讓上傳失敗，並保留 journal 給下一次嘗試。

它完成了，然後說它不確定

然後整個傳過去了。全部 500 GB。日誌上寫著：上傳的完成狀態不確定，請手動確認物件。

我們去 R2 看。物件在：536,870,912,000 個位元組、9,847 段、metadata 裡有我們的 commit 標記、沒有殘留的分段上傳。一次完全的成功被回報成失敗。

RocketBucket 送出最後的 Complete 請求時，會在物件上蓋一個隨機的 token，這樣萬一回應丟了，事後可以問 server：「物件在嗎？帶著我的 token、是我的大小嗎？」並且確定答案講的是自己這次上傳，而不是別人同樣大小的檔案。這個問題在這種規模下有時間差。R2 回應了 Complete，然後花幾十秒把 9,847 片組裝成一個物件。在那段時間裡，物件還不存在，而分段上傳已經不見了。我們的檢查看到「上傳不見了、物件不在」，試了三次、每次最多間隔四秒，然後判定它無法得知。

現在它會用一個大型完成該有的耐心等——六次，2、4、8、15、15、15 秒——並且把「上傳不見了」當成模糊，而不是失敗。什麼算成功沒有改變：物件必須回應、帶著我們的 token、而且大小完全等於預期。token 或大小不對，我們仍然說不確定。我們寧可承認不確定，也不要認領一個不是我們的物件。

設計文件裡每一種情況都有一節，每一節都是對的。失敗在設計文件不會有的三樣東西裡：一個配置器、一個會長大的檔案、一台需要半分鐘把九千片黏起來的 server。這些不是 review 能找到的。是把 500 GB 傳上去才找到的。

目前狀態。同一 session 與跨 session 的續傳都在現在的版本裡，適用於本機檔案上傳到 S3 相容儲存。雲到雲的續傳（比如 S3 → R2）目前仍會重新讀取來源，因為還沒有依範圍讀取的機制；帶 Range 的 GET 是下一項工作。

500 GB は上がった。アプリは「確信がない」と言った

2026 年 9 月 8 日 · S3 と R2 への再開可能アップロード

500 GB のファイルを RocketBucket で Cloudflare R2 に送りました——9,847 パート。中断したアップロードを再開する設計は 5 回のレビューを経ていて、誰の目にも正しく見えました。それでもこの一回は 3 回失敗し、そのどれも設計の中にはありませんでした。

「再開」が約束しなければならないこと

S3 と、その API を話すすべてのサービスは、大きなファイルをパートに分けてアップロードします。最大 10,000 パート、各パートは 5 MiB から 5 GiB。500 GB だとこの算術がパートを最低 52 MB に強制するので、RocketBucket は普段の 8 MiB のデフォルトを捨て、アップロード開始前にこのファイルには 52 MiB を選びます。同時に 5 パートが飛んでいる——およそ 260 MB のメモリで、これが転送に必要な予算の全部のはずです。

6,000 パート目で接続が切れたとき、「再開」とは同じアップロード ID を使い続け、その 6,000 パートを送り直さないことです。口に出せば危険は明らかです。その間にファイルが変わっていたら？ 古いファイルの前半に新しいファイルの後半を貼り付け、サーバーは喜んでそれをオブジェクトと呼ぶでしょう。だからすべてのパートは、最初に完全に読まれた時点で記録されます——番号、バイト数、SHA-256。そしてパートがスキップされるのは、サーバー上に存在し、かつその記録と一致するときだけです。セッションをまたぐ場合、記録はディスク上の小さなジャーナルに置かれ、パートが実際に成功した後にだけ書かれ、完了が証明された後にだけ削除されます。サーバーの ETag を信じるのではなく自分で SHA-256 を持つのは、SSE-KMS の下では ETag がパートの MD5 ではなく、比較する相手がないからです。

もうひとつ、他のツールを見て学んだルール。未完了のマルチパートアップロードは通常のリストには見えず、誰かが中止するまで課金され続けます。RocketBucket はそれらを表示しますが、自分が作ったものでなければ決して中止しません。別のクライアントのものかもしれないからです。

9,800 パートをスキップするのに 14.5 GB のメモリ

500 GB のアップロードを中断し、再開しました。メモリは 14.5 GB まで登り、macOS がプロセスを殺しました。同じファイルを最初からアップロードすると 700〜900 MB に収まります。

最初の容疑者はジャーナルでした。パートごとにファイル全体を書き直していたのです——10,000 パートなら、書くたびに育っていく JSON 文書を 10,000 回書き直す、ディスク上の二乗の仕事。64 パートごとにまとめて書くようにし、書き込み失敗は黙って消えるのではなく保留のまま残るようにして、もう一度走らせました。メモリは 14.5 GB まで登り、macOS がプロセスを殺しました。この修正は正しく、そしてそれは修正ではありませんでした。

本当の原因は「スキップ」の実装にありました。スキップの前にパートを検証するため、再開処理はファイルを 0 バイト目から読み、すべてのパートをハッシュしていました——すでにサーバー上にある 9,800 パートも含めて——一度も止まらない密なループの中で。各パートは小さな一時オブジェクトの雲を残し、そのひとつは恥ずかしいものでした。16 進エンコードに String(format:) を使っていて、1 バイトごとに Objective-C の文字列をひとつ確保していたのです。誰も回収しない、およそ 127,000 個の小さな確保。

構造的な修正はこうです。ジャーナルがあり、ソースがローカルファイルなら、欠けているパートだけをバイト範囲で読み、すでにアップロード済みのものには一切触れない。それらの内容はファイルの同一性——サイズ、更新日時、そして inode（同サイズの差し替えを捕まえるため）——とジャーナルのハッシュが保証します。すべてのパートがすでにある再開は、いまディスクから 0 バイトを読み、0 回のアップロードを発行します。10,000 パートの規模でまさにそれを断言するテストがあります。かつて死んでいた実物の 500 GB 再開は、欠けがなければ 500 MB 未満に、欠けを埋めている間はおよそ 700 MB〜1 GB に収まるようになりました。

レビューが、速い経路が飛ばしたものを見つけた

範囲読みの速い経路はレビューに出され、必須修正を 2 つ持ち帰りました。範囲読みが要求したすべてのバイトを返したか確認していなかった——最後のパートが短く読まれれば切り詰められたオブジェクトが完了し、サーバーはそれを受け入れたでしょう。そして CompleteMultipartUpload を直接呼び、遅い経路が持っていた照合ロジックを飛ばしていました。どちらも修正済みです。短い読みはいまアップロードを失敗させ、次の試行のためにジャーナルを残します。

終わった、そして「確信がない」と言った

そして全部が通りました。500 GB すべて。ログにはこうありました。アップロードの完了は不確かです。オブジェクトを手動で確認してください。

R2 を確認しました。オブジェクトはそこにありました。536,870,912,000 バイト、9,847 パート、メタデータには私たちのコミット印、残されたマルチパートアップロードはなし。完全な成功が失敗として報告されたのです。

RocketBucket は最後の Complete リクエストを送るとき、オブジェクトにランダムなトークンを刻みます。応答が失われても、後からサーバーに「オブジェクトはあるか、私のトークンを持っているか、私のサイズか」と尋ね、その答えが他人の同サイズのファイルではなく自分のアップロードについてだと分かるように。この問いには、この規模だとタイミングの問題があります。R2 は Complete を受け付けたあと、9,847 片をひとつのオブジェクトに組み立てるのに数十秒かけます。その間、オブジェクトはまだ存在せず、マルチパートアップロードはもう消えています。私たちの確認は「アップロードは消え、オブジェクトは不在」を見て、最大 4 秒間隔で 3 回試し、知ることはできないと結論しました。

いまは大きな完了にふさわしい待ち方をします——6 回、2、4、8、15、15、15 秒——そして「アップロードが消えている」を失敗ではなく曖昧として扱います。何を成功とするかは変わっていません。オブジェクトが応答し、私たちのトークンを持ち、期待どおりのサイズであること。トークンかサイズが違えば、やはり「確信がない」と言います。自分のものでないオブジェクトを名乗るより、不確かさを認めるほうを選びます。

設計文書にはこれらの状況すべてに節があり、すべての節は正しかった。失敗は、設計文書に含まれない 3 つのものの中にありました。アロケータ、育つファイル、そして九千片を貼り合わせるのに 30 秒を要するサーバー。これらはレビューでは見つかりません。500 GB をアップロードして見つかるのです。

現在の状態。同一セッションとセッションをまたぐ再開は、S3 互換ストレージへのローカルファイルのアップロードについて現在のビルドに入っています。クラウド間の再開（たとえば S3 → R2）はまだソースを読み直します。バイト範囲の読み手がないためで、Range 付き GET が次の作業です。

500 GB는 올라갔다. 앱은 확신이 없다고 했다

2026년 9월 8일 · S3와 R2로의 이어올리기

500 GB 파일을 RocketBucket으로 Cloudflare R2에 올렸습니다 — 9,847개 파트. 중단된 업로드를 이어가는 설계는 다섯 차례 리뷰를 거쳤고, 누가 봐도 옳았습니다. 그런데도 이 한 번의 실행은 세 번 실패했고, 그중 어느 것도 설계 안에 있지 않았습니다.

"이어올리기"가 약속해야 하는 것

S3와 그 API를 말하는 모든 서비스는 큰 파일을 파트로 나눠 올립니다. 최대 10,000개, 각 파트는 5 MiB에서 5 GiB 사이. 500 GB라면 이 산술이 파트를 최소 52 MB로 강제하므로, RocketBucket은 평소의 8 MiB 기본값을 버리고 업로드가 시작되기 전에 이 파일을 위해 52 MiB를 고릅니다. 동시에 다섯 파트가 날아가고 — 약 260 MB의 메모리, 이것이 한 번의 전송에 필요한 예산 전부여야 합니다.

6,000번째 파트에서 연결이 끊기면, "이어올리기"란 같은 업로드 ID를 유지하고 그 6,000개를 다시 보내지 않는다는 뜻입니다. 위험은 입 밖에 내면 명백합니다. 그 사이에 파일이 바뀌었다면? 옛 파일의 앞부분에 새 파일의 뒷부분을 붙이게 되고, 서버는 기꺼이 그것을 오브젝트라 부를 것입니다. 그래서 모든 파트는 처음 완전히 읽힌 순간 기록됩니다 — 번호, 바이트 수, SHA-256 — 그리고 파트는 서버에 있으면서 동시에 그 기록과 일치할 때만 건너뜁니다. 세션을 넘어서는 경우 기록은 디스크의 작은 저널에 살고, 파트가 실제로 성공한 뒤에만 쓰이며, 완료가 증명된 뒤에만 지워집니다. 서버의 ETag를 믿지 않고 우리 자신의 SHA-256을 두는 이유는, SSE-KMS 아래에서는 ETag가 파트의 MD5가 아니라 비교할 대상이 없기 때문입니다.

다른 도구들을 보며 배운 규칙이 하나 더 있습니다. 미완료 멀티파트 업로드는 일반 목록에 보이지 않고, 누군가 중단하기 전까지 계속 과금됩니다. RocketBucket은 그것들을 보여주지만, 자기가 만들지 않은 것은 절대 중단하지 않습니다. 다른 클라이언트의 것일 수 있으니까요.

9,800개 파트를 건너뛰는 데 14.5 GB의 메모리

500 GB 업로드를 중단하고 다시 이어갔습니다. 메모리가 14.5 GB까지 올라갔고 macOS가 프로세스를 죽였습니다. 같은 파일을 처음부터 올리면 700~900 MB에 머무릅니다.

첫 용의자는 저널이었습니다. 파트마다 파일 전체를 다시 썼던 것입니다 — 10,000개 파트라면 쓸 때마다 커지는 JSON 문서를 10,000번 다시 쓰는, 디스크 위의 제곱 작업. 64개 파트마다 모아서 쓰게 하고, 실패한 쓰기는 조용히 사라지지 않고 보류 상태로 남게 한 뒤 다시 돌렸습니다. 메모리가 14.5 GB까지 올라갔고 macOS가 프로세스를 죽였습니다. 그 수정은 옳았고, 그것은 수정이 아니었습니다.

진짜 원인은 "건너뛰기"의 구현에 있었습니다. 건너뛰기 전에 파트를 검증하기 위해, 이어올리기 과정은 파일을 0바이트부터 읽어 모든 파트를 해시했습니다 — 이미 서버에 있는 9,800개까지 — 한 번도 멈추지 않는 빽빽한 루프 안에서. 파트마다 작은 임시 객체 구름을 남겼고, 그중 하나는 민망했습니다. 16진 인코딩에 String(format:)을 썼는데, 바이트 하나마다 Objective-C 문자열을 하나씩 할당합니다. 아무것도 회수하지 않는 약 127,000개의 작은 할당.

구조적인 수정은 이렇습니다. 저널이 있고 소스가 로컬 파일이면, 빠진 파트만 바이트 범위로 읽고 이미 올라간 것은 전혀 건드리지 않습니다. 그 내용은 파일의 정체성 — 크기, 수정 시각, 그리고 inode(같은 크기로 바꿔 넣은 파일을 잡아내기 위해) — 와 저널의 해시가 보증합니다. 모든 파트가 이미 있는 이어올리기는 이제 디스크에서 0바이트를 읽고 0번 업로드합니다. 10,000개 파트 규모에서 정확히 그것을 단언하는 테스트가 있습니다. 예전에 죽던 실제 500 GB 이어올리기는 이제 빠진 것이 없으면 500 MB 아래에, 빈틈을 채우는 동안에는 약 700 MB~1 GB에 머무릅니다.

리뷰가 빠른 경로가 건너뛴 것을 찾았다

범위 읽기 빠른 경로는 리뷰에 올라갔고 두 개의 필수 수정을 들고 돌아왔습니다. 범위 읽기가 요청한 바이트를 모두 돌려줬는지 확인하지 않았다 — 마지막 파트가 짧게 읽히면 잘린 오브젝트가 완료되고 서버는 그것을 받아들였을 것입니다. 그리고 CompleteMultipartUpload를 직접 호출해, 느린 경로가 가진 대조 로직을 건너뛰었습니다. 둘 다 고쳤습니다. 짧은 읽기는 이제 업로드를 실패시키고 다음 시도를 위해 저널을 남깁니다.

끝났다, 그리고 확신이 없다고 했다

그리고 전부 올라갔습니다. 500 GB 모두. 로그에는 이렇게 적혔습니다. 업로드 완료 여부가 불확실합니다. 오브젝트를 직접 확인해 주세요.

R2를 확인했습니다. 오브젝트는 거기 있었습니다. 536,870,912,000바이트, 9,847개 파트, 메타데이터에 우리의 커밋 표식, 남은 멀티파트 업로드는 없음. 완전한 성공이 실패로 보고된 것입니다.

RocketBucket은 마지막 Complete 요청을 보낼 때 오브젝트에 무작위 토큰을 찍습니다. 응답을 잃어도 나중에 서버에 "오브젝트가 있는가, 내 토큰을 갖고 있는가, 내 크기인가"를 물어, 그 답이 남의 같은 크기 파일이 아니라 자기 업로드에 관한 것임을 알 수 있도록. 이 질문에는 이 규모에서 타이밍 문제가 있습니다. R2는 Complete를 받아들인 뒤 9,847조각을 하나의 오브젝트로 조립하는 데 수십 초를 씁니다. 그 동안 오브젝트는 아직 존재하지 않고 멀티파트 업로드는 이미 사라져 있습니다. 우리의 확인은 "업로드는 사라졌고 오브젝트는 없다"를 보고, 최대 4초 간격으로 세 번 시도한 뒤 알 수 없다고 결론지었습니다.

이제는 큰 완료에 어울리는 방식으로 기다립니다 — 여섯 번, 2, 4, 8, 15, 15, 15초 — 그리고 "업로드가 사라졌다"를 실패가 아닌 모호함으로 다룹니다. 무엇이 성공인지는 바뀌지 않았습니다. 오브젝트가 응답하고, 우리 토큰을 갖고, 정확히 기대한 크기여야 합니다. 토큰이나 크기가 다르면 여전히 확신이 없다고 말합니다. 우리 것이 아닌 오브젝트를 우리 것이라 주장하기보다 불확실함을 인정하는 편을 택합니다.

설계 문서에는 이 모든 상황에 대한 절이 있었고, 모든 절은 옳았습니다. 실패는 설계 문서에 들어 있지 않은 세 가지 안에 있었습니다. 할당자, 자라나는 파일, 그리고 구천 조각을 붙이는 데 30초가 필요한 서버. 이런 것들은 리뷰로 찾지 못합니다. 500 GB를 올려 봐야 찾습니다.

현재 상태. 같은 세션과 세션을 넘어서는 이어올리기는 S3 호환 스토리지로의 로컬 파일 업로드에 대해 현재 빌드에 들어 있습니다. 클라우드 간 이어올리기(예: S3 → R2)는 아직 소스를 다시 읽습니다. 바이트 범위 읽기가 없기 때문이며, Range를 붙인 GET이 다음 작업입니다.
