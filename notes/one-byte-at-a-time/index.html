One byte at a time: why downloads were 28× slower than uploads, and why a thousand small files waited in line

November 3, 2026 · RocketBucket 0.3.0 (next release)

TL;DR
  • Small files: we used to send one file at a time. Now many go at once, sharing one limit on connections and memory. Uploading 1,000 files of 100 KB went from 10.05 s to 0.72 s.
  • Downloads: downloading 1 GiB took 31 s; uploading the same file took 1 s. 97% of the CPU time went to one line of code, the one that appended incoming data one byte at a time. Once each chunk is handled as a whole, the 1 GiB download takes 0.48 s, and 5 GiB went from 160 s to 7.3 s.
  • Retries: only multipart uploads of large files used to retry; small-file uploads and every download failed on a single 503. Now every request retries on its own, waiting longer each time and honoring the server's Retry-After.
  • One hour: any download that ran past 60 minutes was always cut off. Not anymore.
  • All numbers were measured on an M4 Mac mini against a local MinIO. Over a real network the ratios will differ, but the bottlenecks are real. These improvements ship in the next release, 0.3.0.

The previous note was about one 500 GB file. This one is about the other end: a thousand small files, and getting files back from the cloud. Both are ordinary jobs, both were more than an order of magnitude slower than they should have been, and in neither case was the network to blame.

A thousand files, one after another

It started with reading FileMoverExpress, which AWS open-sourced. It picks its kind of parallelism by file size: a large file is split into many parts sent at once, while small files go many files at a time. Looking back at RocketBucket, we had the large-file half, five parts at once, and none of the small-file half. The transfer engine was a for loop that started the next file only when the previous one was done.

For a 100 KB file the data itself takes almost no time. The time goes into waiting: first ask the destination "is this file there?", then ask the source "how big are you?", and only then upload. Three round trips, one after another. A thousand files means three thousand waits in a row. The bandwidth sat almost empty.

Making the loop parallel was not enough, because two limits sat underneath it. By default, URLSession on macOS opens at most 6 connections to one host, and S3 speaks HTTP/1.1, so setting the concurrency to 100 still left only 6 requests running. And every transfer created a new session that was never reused and never shut down.

Now one shared "budget" governs two things: how many requests are in flight, and how many bytes are buffered in total (256 MiB). Small files and the parts of large files draw from the same budget, so dropping in ten thousand small files at once, or sending three large files together, cannot make memory run away. The connection limit is raised to match the budget, and the same bucket with the same credentials shares one long-lived session.

That took the upload from 10.05 s to 0.72 s.

One byte at a time

Downloading 1 GiB took 31 s, while uploading the same file took 1 s. Against a local MinIO, the network cannot be the reason.

Profiling showed it: one CPU core pinned, and 97% of the samples in the same place. Swift's URLSession.AsyncBytes hands out data one byte at a time, and our code kept its pace, appending to a Data one byte at a time. 1 GiB is a billion appends. Each one is cheap; together they cost 31 s.

The fix was to switch to a delegate: when the network delivers a chunk, we take the whole chunk. 1 GiB became 0.48 s, and user CPU dropped from 30 s to 0.25 s. 5 GiB went from 160 s to 7.3 s; at that size the bottleneck is the SSD and the memory cache, no longer our code.

While we were there, we added a check that should have existed all along: the number of bytes received must equal the Content-Length the server declared. If it does not, the download fails, instead of a truncated file being renamed into place as the real one.

Ranged downloads

A large file downloaded to the Mac is now split into several ranges fetched at once. Each range is written with pwrite to its own offset in a temporary file, and the file gets its real name only when all of them are in. Every range is pinned to the object's ETag: if someone replaces the file mid-download, the next range request is refused and the whole download fails, rather than stitching together a file that is half old and half new. Each range can be retried on its own.

To be honest, this one shows no gain against a local MinIO, where a single connection already runs at full speed. Its value is on real networks: many paths cap the speed of a single connection, and that is where fetching several ranges at once makes the difference.

One hour

URLSession has two timeouts. One is "how long with nothing received", which we set to 30 s; the other is "how long the whole request may take", which we had set to 3600 s. Uploads are cut into many parts, each of them short, so they never hit the second one. A download, though, is one request read from start to finish: a 100 GB file at 25 MB/s takes 67 minutes, and was always cut off at minute 60.

The overall limit is now 7 days, and deciding whether the connection is still alive is left to the 30-second one.

Retries, and what must not be retried

Before, only multipart uploads of large files retried, and they redid the whole round: re-reading the source from byte 0 and re-hashing every part. Small-file uploads, downloads, listings and HEAD requests failed on a single 503.

Now every request has its own retries. The wait grows exponentially, with random jitter so a crowd of requests does not slam back all at once; if the server sends Retry-After, we wait that long; if the credentials have expired, we refresh them once and try again.

Review caught two things here. First, some requests must not be resent blindly. If the outcome of "create multipart upload" is unknown, resending it can create two uploads; if the outcome of "complete upload" is unknown, the right move is the reconciliation described in the previous note, not pressing the button again. Neither of these is retried now. Second, after we removed the cap on Retry-After, an absurdly large value (say 10¹¹ s) overflowed when converted to nanoseconds and crashed the app. It is now clamped to the maximum.

One change in behavior

Review also asked a question we had not considered: what happens if a small file grows after it is scanned but before it is read? The answer was that we would read the whole thing into memory at its new size, while the memory budget had been reserved for the old one.

We chose to make it fail. As soon as what we read exceeds the size seen at scan time, that file stops for this run with the error Source size changed, which is how large files have always behaved. A file that is still being written will not be uploaded this time; run the transfer again and it will be. We would rather skip a half-written file than upload one you believe is complete.

Where this stands. These improvements ship in the next release, 0.3.0. A cloud-to-cloud transfer (S3 → R2, say) still reads the whole source in one request and starts over from the beginning on a retry; moving it to ranged reads too is the next piece of work (#15). Letting the cloud do the copy within the same provider, without passing through your Mac, is also on the list.
